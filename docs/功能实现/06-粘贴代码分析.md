# 06 · 粘贴代码分析

> 在对话里直接贴源码：「有什么问题？怎么改？」——**当场改写建议**，不做全仓工程审核，也不动 Git/本机工程。

---

## 1. 实现原理

### 1.1 三种「和代码有关」的能力，别混

工程师在对话里贴代码时，需求可能是三种完全不同的事：

| 能力 | 你看的是什么 | 输出 | 会不会动工程 |
|------|--------------|------|--------------|
| **贴码分析**（本篇） | 消息里那一段代码块 | 对话里给问题和改法 | 否 |
| **代码审核** | 整个 Git 仓 / IDE 工程 | P0/P1/P2 审核报告 | 否（只读） |
| **写码** | 本机目录 / GitHub 仓 | 真改文件 | 是（确认后） |

贴码分析的定位是：**轻量、即时、只看眼前这一段**——像同事帮你瞟一眼 snippet，不需要克隆仓库、不需要开 VS Code Bridge。

### 1.2 怎么防止「贴码」被当成「审仓」或「写仓」？

1. **前端车道**  
   `chatIntent.js` 识别到代码块 +「有什么问题/怎么改」→ 设置 `workbuddy_lane=paste_code`，随 SSE 请求带给后端。

2. **后端车道解析**  
   `workbuddy_lanes.py` 登记 `LANE_PASTE_CODE`，与 `code_review`、`code_dev` 互斥。

3. **系统提示硬约束**  
   `agent.py` 里 `_PASTE_CODE_ANALYZE_PROMPT`：  
   - 禁止调 `request_git_*`、`request_ide_*`  
   - 禁止输出 `## 🔍 代码审核报告` 那种全仓报告壳  
   - 禁止突然弹出写码选仓卡

4. **Skill**  
   `paste-code-analyze` 规定交付形态：问题列表 → 建议 →（用户短确认后）完整改写代码，全在对话气泡里完成。

### 1.3 短确认怎么理解？

用户第一轮问完，模型说「我可以给你一版改好的」；用户回「来吧 / 好的」——  
系统提示要求**立刻贴出完整代码**，不要又去做 PCB 科普或平台能力介绍。这是会话续写规则，不是新开会话。

### 1.4 依赖什么？

- 配好 LLM 即可  
- 不需要 Git、不需要 IDE 配对、不需要 Cursor Key

## 2. 实现流程（技术点怎么落地）

> 贴码 = **纯 SSE + 专用 lane 提示**；无 Git clone、无 IDE Bridge、无 Job API。

### 2.1 意图识别与 lane 注入

```text
用户消息含 ``` 代码围栏 +「有什么问题/怎么改」
  → looksLikePasteCodeAnalyze(text)（chatIntent.js）
       内部：looksLikeRawPastedCode + 问题/改法关键词
  → ChatView send() 设置 page_context.workbuddy_lane = 'paste_code'
  → POST /api/chat/stream
```

| 技术点 | 实现 |
|--------|------|
| 与审码互斥 | 含 Git URL +「审核」→ `looksLikeCodeReview`，不走贴码 |
| 与写码互斥 | 「在本机工程加功能」→ `looksLikeCodeDevIntent` |
| 后端清洗 | `sanitize_page_context_lanes()` 丢弃非法 lane 值 |

### 2.2 Agent 侧：提示块 + Skill

```text
resolve_workbuddy_lane() === LANE_PASTE_CODE
  → agent.py 注入 _PASTE_CODE_ANALYZE_PROMPT
  → 加载 Skill paste-code-analyze/SKILL.md

硬约束：
  - 禁止 request_git_* / request_ide_*
  - 禁止输出「## 🔍 代码审核报告」全仓报告壳
  - 禁止 :::cursor_dev_* 写码围栏
```

模型通常**无 tool call**，直接在上下文里读用户贴的代码块作答。

### 2.3 标准对话时序

```text
轮次 1：用户贴代码 + 问问题
  → 模型：问题列表 → 修改建议（可含局部 diff 说明）
  → SSE token 流式；ChatView 渲染 Markdown 代码块

轮次 2（可选）：用户「来吧 / 好的」
  → 同会话 checkpoint 续写
  → 模型须直接输出完整改后代码
  → 禁止再开 PCB 科普或平台能力介绍（Skill + 系统提示）
```

交付物只在**消息气泡**；不写磁盘、不创建 Job。

### 2.4 与审码 / 写码分流对照

| 用户说法 | 意图函数 | lane | 会不会动工程 |
|----------|----------|------|--------------|
| 贴 20 行 +「有啥 bug」 | `looksLikePasteCodeAnalyze` | `paste_code` | 否 |
| 「审 https://github.com/xx」 | `looksLikeGitRepoReview` | `code_review` | 否（只读克隆） |
| 「本机工程加登录页」 | `looksLikeCodeDevIntent` | `code_dev` | 是（Job 后） |

### 2.5 常见排查

| 现象 | 查什么 |
|------|--------|
| 弹出 Git 选仓卡 | lane 是否误为 `code_review` |
| 弹出写码确认卡 | lane 是否误为 `code_dev`；模型是否输出了围栏 |
| 短确认后又科普 | `paste-code-analyze` Skill 是否加载 |
| 要审全仓 | 引导用户改说「审核仓库」走功能 07 |

## 3. 技术及用法

| 技术 / 模块 | 怎么用 |
|-------------|--------|
| `apps/web/src/chatIntent.js` | 识别贴码分析意图 |
| `ChatView.vue` | `pasteCodeStreamOpts`、lane 传递 |
| `apps/api/workbuddy_lanes.py` | `LANE_PASTE_CODE` |
| Skill `paste-code-analyze` | 对话交付代码；无 Bridge |
| `agent.py` 内贴码专用提示块 | 禁审核工具、禁报告壳 |

无单独环境开关；依赖 LLM 配置即可。

---

## 4. 后续扩展与优化建议

1. **可做**：语言/框架探测后给更贴栈的检查清单（仍对话交付）。  
2. **可做**：一键「把这段改动提交到写码车道」的显式按钮（须再确认，勿自动）。  
3. **不要做**：贴码分析偷偷克隆仓库或写本机文件。  
4. **不要做**：与全仓审码报告格式混用，导致用户以为已经审完工程。

## 自测话术

- 贴一段有明显空指针风险的 JS/Python，问「有什么问题」。  
- 回「来吧」应直接给完整修改，而不是选仓卡。
