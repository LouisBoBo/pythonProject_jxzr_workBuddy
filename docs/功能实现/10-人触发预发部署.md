# 10 · 人触发预发部署

> 用户说「部署到预发」→ **确认卡** → API 触发 **本机 SSH** 或 **GitHub Actions**，把业务项目发到预发环境；可探活访问地址。**默认关**；**不自动上生产**。

---

## 1. 实现原理

### 1.1 产品里的「自动化部署」指什么？

不是「AI 写完代码自动上生产」，而是：

> 人说「部署到预发」→ 看清确认卡 → 点确认 → **后台程序**按配置把指定版本同步到预发机并重启服务。

模型**不参与** SSH、不参与 `rsync`、不持有私钥内容。和提交一样，是 **API 旁路执行**。

### 1.2 总开关与环境白名单

| 配置 | 含义 |
|------|------|
| `DEPLOY_ENABLED` | 总开关，默认 **关**；须在设置页打开并点「保存并热更新」 |
| `DEPLOY_ENV_WHITELIST` | 允许部署的环境名，默认含 `staging` |
| `DEPLOY_ALLOW_PRODUCTION` | 是否允许生产（默认关；P1-3e 治理缓开） |

拨钮变灰、第二天又关：常见原因是**没保存到 settings.json**，或单测曾污染 `DATA_DIR`（已用临时目录隔离修复）。

### 1.3 两种执行器（二选一）

`DEPLOY_CI_PROVIDER`：

| 值 | 适用 | 实际干什么 |
|----|------|------------|
| `local_ssh` | 国内预发机、GitHub Actions 连不上 :22 | 本机 `git worktree` 检出 → 按配置 `npm build` 等 → **SSH + rsync** 到远端 → 可选 `systemctl restart` → HTTP 探活 |
| `github_actions` | 境外 runner 能 SSH 或仓内自建流水线 | 调 GitHub API `workflow_dispatch` → 轮询 run 状态 |

江西中软现场：**境外 Actions 连国内轻量 :22 经常失败**，所以主推 `local_ssh`；Actions 路径仍保留作备选。

### 1.4 配置为什么要「可换项目」？

早期写死 `frontend/` + `backend/` + `npm run build`。  
现在支持在设置里配：

- `DEPLOY_SSH_SYNC_PAIRS`：本地目录 → 远端目录  
- `DEPLOY_SSH_BUILD_STEPS`：构建命令白名单（禁 `shell=True`、禁 `-c` 注入）  
- `DEPLOY_SSH_RSYNC_EXCLUDES`：不同步 `.env`、`node_modules` 等  

留空则仍用 monorepo 默认，兼容 `pythonProject_zr_aicoding` 布局。

### 1.5 探活（P1-3d）

部署成功后可选访问 `DEPLOY_HEALTH_URL`（如 `http://IP:8090/`），2xx 才算健康，结果写回确认卡。  
**查数验收**（部署后再查一条 MES）仍可选，未强制接入。

### 1.6 安全要点（已落地）

- SSH 私钥路径在本机（如 `~/.ssh/tc_staging_deploy`），settings 只存路径  
- 同步路径 `resolve` + `relative_to`，拒绝 `..` 穿越  
- `/deploy/poll` 未配置仓时拒绝客户端随意传 `repo`（防 Token 滥用）  
- confirm 有锁，防连点两次部署  
- 浅路径 + `rsync --delete` 组合会拒绝（防误删 `/www/wwwroot`）

## 2. 实现流程（技术点怎么落地）

> 下面按真实代码路径写。核心约定：**模型不参与 SSH / rsync / Actions**；人点确认后由 FastAPI 直调 `deploy_*.py`。

### 2.1 意图识别：为什么一句话不进 Agent？

```text
用户输入 → ChatView.vue 发送前先跑 chatIntent.js
         → looksLikeDeploy(text) === true
         → 直接 prepareLocalDevDeploy({ message })
         → 不走 POST /api/chat/stream（Deep Agents）
```

**技术点：**

| 点 | 怎么做的 |
|----|----------|
| 关键词匹配 | `apps/web/src/chatIntent.js` 的 `looksLikeDeploy`：匹配「部署到预发 / 发布到 staging / 部署到测试」等；内部再调 `_looksLikeDeployCore` |
| 意图互斥 | 同一句若像部署，提交批 `looksLikeLocalCommitBatch` 会返回 false，避免一条话同时开两条危险链路 |
| 优先级 | ChatView 发送顺序里 **部署排在提交、写码前面**：先命中就走部署卡 |

**为什么这样设计：** 部署是「开关 + 配置 + 确认」问题，不需要大模型再理解一遍；也不希望模型幻觉「已部署」。

### 2.2 prepare：只做门禁检查，绝不发版

```text
前端 api.js → POST /api/local-dev/deploy/prepare
           → routes/local_dev.py::prepare_local_dev_deploy（须登录）
           → deploy_prepare.prepare_deploy(...)
```

`prepare_deploy`（`deploy_prepare.py`）逐步干这些事：

#### （1）猜环境、定 ref

| 输入 | 处理 |
|------|------|
| 用户原话含「生产 / production」 | `target_env = production`（仍可能被白名单挡下） |
| 含「预发 / staging / 测试」 | `target_env = staging` |
| 都没有 | `default_deploy_env()`（白名单第一项，常为 staging） |
| `ref` 空 | `default_deploy_ref()` ← `DEPLOY_DEFAULT_REF` 或 `LOCAL_DEV_WORK_BRANCH`（如 `hebo`） |

#### （2）读配置快照

`get_deploy_config()` 从环境变量 + `settings.json` 合成 `DeployConfig`（总开关、provider、白名单、SSH/GitHub 字段、探活 URL 等）。

#### （3）逐项检查，填 `checks[]` / `blocking_reasons[]`

| 检查 id | 过关条件 | 失败时用户看到 |
|---------|----------|----------------|
| `enabled` | `DEPLOY_ENABLED` 为真 | 「总开关关闭」——拨钮未保存常见于此 |
| `env` | `env_allowed(target_env)` | 「环境未授权」；生产默认不在白名单 |
| `ci`（local_ssh） | `validate_local_ssh_settings` 全过 | 缺主机/用户/私钥路径/本机项目路径等 |
| `token`（local_ssh） | 私钥路径已配且像私钥文件 | 本机路径校验，**不读私钥进对话** |
| `ci`（github） | 配了 `DEPLOY_GITHUB_REPO` + workflow 名 | 「GitHub Actions 未配齐」 |
| `token`（github） | `DEPLOY_GITHUB_TOKEN` 或 `GITHUB_TOKEN` 非空 | 「未配置 Token」→ `can_trigger_ci=false` |

#### （4）local_ssh 额外校验（`validate_local_ssh_settings`）

代码里会硬拦这些坑：

- 本机项目路径必须是 **git 仓**（有 `.git`）
- 私钥文件须存在，且内容像 `BEGIN … PRIVATE KEY`（防把公钥路径填进去）
- 远端 `DEPLOY_SSH_APP_PATH` 不能过浅（禁止 `/`、`/www`、`/www/wwwroot`），避免 `rsync --delete` 误删整站
- Host 不能写成 `IP:22`（端口另字段）；`restart_cmd` 须匹配白名单正则（禁止 `;` `` ` `` `$()` 等注入）

#### （5）返回给前端的关键字段

```text
ready_for_confirm / can_trigger_ci
env / env_label / ref
ci_provider（local_ssh | github_actions）
blocking_reasons[]、checks[]
health_url / visit_url（成功后展示用）
ssh_host、local_project_path（仅 local_ssh 展示）
```

**此阶段保证：** 不 `git worktree`、不 `rsync`、不调 GitHub `dispatches`。只生成确认卡数据。

#### （6）前端怎么画卡

`ChatView` 收到 prepare 结果 → 挂 `LocalDevDeployGateCard`：

- 展示环境、ref、本机 SSH 目标或 Actions 仓库/workflow
- 有 blocker 时按钮灰掉或只允许「取消」
- 用户可改 ref 后再确认（以 confirm 入参为准）

### 2.3 confirm：再检一次门禁 + 防双击 + 分流执行器

```text
用户点「确认部署」
  → POST /api/local-dev/deploy/confirm
     body: { decision, env?, ref?, message? }
  → confirm_deploy(...)（deploy_confirm.py）
```

#### （1）decision 分流

| decision | 行为 |
|----------|------|
| `cancel` / `skip` | 直接返回「已取消，未触发」 |
| `confirm` / `deploy` / `ok` | 进入发版逻辑 |
| 其它 | `400`：decision 非法 |

#### （2）确认时**再跑一遍** `prepare_deploy`

防止：卡弹出来之后有人关了 `DEPLOY_ENABLED`、改坏了私钥路径，却仍点确认。  
`ready_for_confirm=false` → 立刻 `ok=False`，不进执行器。

#### （3）ref 安全校验（两家执行器共用）

```text
不允许含 ".."
必须匹配 ^[A-Za-z0-9._/\-]+$
```

防路径穿越式 ref（例如 `../../etc/passwd` 这种恶意字符串进 `git worktree`）。

#### （4）短窗幂等（防双击）

```text
key = "{user_id}|{env}|{ref}|{provider_key}"
进程内字典 _RECENT + threading.Lock
90 秒内同 key 再点 → status=duplicate，拒绝第二次触发
```

**技术点：** 先写入 `_RECENT` 再调执行器，避免两个并行请求都通过时间窗检查。  
重启 API 后字典清空（可接受：最多再部署一次）。

#### （5）按 `ci_provider` 调用不同函数

| provider | 调用 | 立即返回给前端什么 |
|----------|------|-------------------|
| `local_ssh` | `trigger_local_ssh_deploy(...)` | `run_id=local-{12位hex}`，任务已在后台线程跑 |
| `github_actions` | `trigger_workflow_dispatch(...)` | GitHub `run_id` / Actions URL（尽力取） |

路由层：`result.ok=false` → HTTP 400 + `detail=error`。

### 2.4 执行器 A：本机 SSH（`deploy_local_ssh.py`）——逐步技术细节

这是国内预发的主路径。整体是一个**后台线程**，状态存在进程内存 `_JOBS`（不是 GitHub）。

#### 步骤 A0 · 创建任务并限流

```text
run_id = "local-" + secrets.token_hex(6)   # 正则：local-[0-9a-f]{12}
同时进行中的部署 > 1 个 → 拒绝（防两路 rsync 互踩）
_JOBS[run_id] = { status: queued → in_progress, log_tail, ... }
threading.Thread(target=_execute_job, daemon=True).start()
```

前端立刻拿到 `run_id`，开始轮询。

#### 步骤 A1 · 临时目录 + worktree 检出（不动用户当前工作区）

```text
work_root = tempfile.mkdtemp(prefix="wb-deploy-")   # 如 /tmp/wb-deploy-xxxx/
src       = work_root / "src"
release   = work_root / "release"

# 先确认 ref 是真实 commit
git rev-parse --verify "{ref}^{commit}"   # cwd=本机项目根

# 再挂临时 worktree（--detach：不切换你 IDE 当前分支）
git worktree add --detach {src} {ref}
```

**为什么用 worktree：** 你可能正在 `hebo` 上改半截代码；部署要的是「已提交的某个 ref」，不能把脏工作区直接 rsync 上去。

任务结束（成功/失败）会 `git worktree remove --force` + 删临时目录。

#### 步骤 A2 · 本机构建（无 `shell=True`）

```text
读 DEPLOY_SSH_BUILD_STEPS（或 monorepo 默认：frontend 里 npm run build 等）
对每一步：
  1. cwd = 项目根下的相对目录，resolve 后必须 relative_to(src_root)（防 .. 逃逸）
  2. 命令字符串经 _safe_build_cmd：只允许 [A-Za-z0-9_./\-+=@: 空格]
  3. shlex.split → argv 列表
  4. 拒绝 token 里出现 ; | & && || > < `
  5. subprocess.run(argv, cwd=cwd, shell=False, timeout=900)
```

日志追加到 `job["log_tail"]`（截断约 4000 字），前端轮询能看到「构建 frontend → npm run build」。

#### 步骤 A3 · 打包到 release 暂存区

```text
按 DEPLOY_SSH_SYNC_PAIRS（默认如 frontend/dist → 远端 frontend/dist）
把构建产物 copytree 进 work_root/release/{local_rel}
```

之后 rsync **只同步 release**，不把整个源码树（含 `.git`、`node_modules`）推上去。

#### 步骤 A4 · SSH 探测 + rsync

```text
# 1) 拼 ssh 基命令（BatchMode=yes：无交互密码；只用公钥）
ssh -i {私钥} -p {port} -o IdentitiesOnly=yes -o BatchMode=yes
   -o StrictHostKeyChecking=accept-new -o ConnectTimeout=20
   -o PreferredAuthentications=publickey
   {user}@{host}  "mkdir -p -- {远端各目录} && echo ssh_ok"

# 2) rsync -e 也是同一套 ssh 参数（路径 shlex.quote，防空格打断）
rsync -az --delete
  --exclude .env --exclude node_modules …（来自 DEPLOY_SSH_RSYNC_EXCLUDES）
  -e "ssh -i …"
  {release/local_rel}/  {user}@{host}:{app}/{remote_rel}/
```

**技术点：**

- `--delete`：远端多余文件会删掉，所以 **APP 路径绝不能浅**（前面 validate 已拦）
- exclude：默认挡住 `.env`、`*.pem`、`.git` 等，避免密钥被同步到预发
- 同步对可配置多对目录（前后端分离 monorepo）

#### 步骤 A5 · 远端重启（可选）

```text
若配置了 DEPLOY_SSH_RESTART_CMD：
  再次校验白名单正则（如 systemctl restart zr-aicoding-api）
  ssh … "bash -lc {shlex.quote(整条命令)}"
```

江西中软示例：只重启 `8009` 上的 API，不动图谱 `8000`。

#### 步骤 A6 · 本机 HTTP 探活（P1-3d）

```text
probe_deploy_health(DEPLOY_HEALTH_URL):
  - 空 URL → skipped，不算失败
  - assert_http_url_allowed：只允许 http/https，拒绝 file://、禁扫内网敏感段（走 safe_http）
  - GET，User-Agent=zr-workbuddy-deploy-health
  - 默认最多 5 次，间隔递增；2xx 通过
  - 非 2xx / 超时 → 整次部署标失败（文件可能已同步，但确认卡会写明「探活失败」）
```

成功时 `job.visit_url = health_url`，卡片直接展示访问地址。

#### 步骤 A7 · 状态机（前端靠这个画过程）

| `status` / 字段 | 含义 |
|-----------------|------|
| `queued` | 已创建，线程未开始 |
| `in_progress` | 检出/构建/同步中 |
| `completed` + `success` | 全流程成功 |
| `completed` + `failed` | 任一步抛错；`message`/`log_tail` 有摘要 |
| `health_ok` / `health_detail` | 探活结果 |

**注意：** `_JOBS` 在 **API 进程内存**。重启 `./scripts/dev.sh` 后旧 `local-*` 查不到——卡片会提示「未找到任务（可能已重启 API）」。

### 2.5 执行器 B：GitHub Actions（`deploy_github.py`）

适合 runner 能连上目标机的场景；国内轻量机常连不上，作备选。

```text
POST https://api.github.com/repos/{owner}/{name}/actions/workflows/{workflow.yml}/dispatches
Header: Authorization: Bearer {DEPLOY_GITHUB_TOKEN}
Body:  { "ref": "hebo", "inputs": { "environment": "staging" } }
期望：HTTP 204
```

**技术点：**

| 点 | 怎么做的 |
|----|----------|
| 仓库名解析 | `owner/name` 正则校验，拒绝随意 URL |
| workflow 名 | 只允许安全文件名字符 |
| inputs 键名 | `DEPLOY_GITHUB_WORKFLOW_ENV_INPUT`（默认 `environment`）；设为 `none` 则不传 inputs |
| 422 降级 | 部分 workflow 无 inputs 会 422 → 自动再试一次仅 `{ref}` |
| 取 run_id | 触发后 sleep 0.8s，再 GET 该 workflow 最近一次 `workflow_dispatch` run（有竞态，失败不阻断） |
| Token | 只在服务端读，不进 Prompt、不回传前端明文 |

真正的构建/SSH 在 **GitHub runner** 上跑（见 `docs/写码与审码/示例-deploy-staging.yml`），WorkBuddy 只负责触发 + 轮询状态。

### 2.6 轮询 poll：前端如何更新过程条

```text
LocalDevDeployGateCard 定时器
  → POST /api/local-dev/deploy/poll
     { run_id, workflow?, ref? }
```

**分支逻辑（`routes/local_dev.py`）：**

```text
若 run_id 以 local- 开头 或 ci_provider=local_ssh：
    → get_local_ssh_run_status(run_id)   # 查内存 _JOBS
否则：
    → 强制使用系统配置的 DEPLOY_GITHUB_REPO
    → 禁止客户端乱传别的 repo（防用服务端 Token 查别人仓）
    → get_workflow_run_status(run_id) 或 find_latest_workflow_run(workflow)
```

| 返回字段 | 前端用途 |
|----------|----------|
| `status` / `done` / `success` | 进度态、成功/失败样式 |
| `message` / `log_tail` | 过程文案（检出、构建、rsync…） |
| `html_url`（Actions） | 「打开流水线」链接 |
| `visit_url` / `health_ok` | 成功后展示预发地址 |
| `unreachable`（GitHub） | 网络暂不可达时 **HTTP 200 + ok=false**，前端继续轮询不崩 |

轮询超时由 `DEPLOY_POLL_TIMEOUT_SEC` / prepare 返回的 `poll_timeout_sec` 控制。

### 2.7 整条链路串起来（一眼版）

```text
说话
  → chatIntent 拦住，不进大模型
  → prepare：读开关/白名单/SSH或Token，画确认卡（零副作用）
  → 人点确认
  → confirm：再检门禁 + 90s 防双击
       ├─ local_ssh：临时 worktree → 安全构建 → rsync → 可选 restart → 探活
       │            状态在 API 内存，run_id=local-…
       └─ github_actions：API dispatches → runner 干活
                    状态在 GitHub，run_id=数字
  → 卡片 poll 直到 done → 成功展示 visit_url / 失败展示 log
```

### 2.8 预发机上的典型布局（江西中软示例）

| 组件 | 说明 |
|------|------|
| Nginx `:8090` | 对外访问 ERP 前端 |
| 后端 `127.0.0.1:8009` | `zr-aicoding-api` systemd |
| 旧图谱 `80/8000` | **不动**，部署脚本只碰 8090/8009 |

### 2.9 和提交的关系

推荐顺序：

```text
写码 → 提交并 push 到工作分支 → 部署（ref 指向该分支或 tag）
```

部署读的是 Git ref，不是「未提交的本地脏文件」。local_ssh 用 worktree 检出的就是这个 ref 的已提交快照。

### 2.10 常见排查

| 现象 | 原因 |
|------|------|
| 按钮总关 | DEPLOY_ENABLED 未保存 |
| Actions 卡 SSH | 境外 runner 连国内机；换 local_ssh |
| 探活失败 | 服务没起来、URL 错、防火墙 |
| 构建失败 | BUILD_STEPS 与项目不符；改设置或留空用默认 |

## 3. 技术及用法

| 技术 / 模块 | 怎么用 |
|-------------|--------|
| `chatIntent.js` `looksLikeDeploy` | 与提交/写码意图互斥 |
| `LocalDevDeployGateCard.vue` | 确认、轮询、探活展示 |
| `SettingsView.vue` 自动化部署分类 | GitHub 与本机 SSH 分区配置 |
| `deploy_local_ssh.py` | SSH、rsync、构建步骤白名单、重启命令校验 |
| `deploy_github.py` | GitHub API 触发与查询（Token） |
| 探活 | HTTP 2xx 重试；非法 scheme 拒绝 |
| 配置族 | `DEPLOY_*`（见 `.env.example` / settings_store） |

安全点（已落地过）：poll 在未配置仓时不接受客户端随意 `repo`；confirm 加锁防重入；浅路径 + `--delete` 拒绝等。

## 4. 后续扩展与优化建议

1. **可做（P1-3e）**：生产二次确认 + 变更窗。  
2. **可做**：部署后「查数验收」接运维/查数 Tools（探活已有，查数验收仍可选）。  
3. **可做**：国内可达 CI（CODING 等）再评估；当前国内预发主推 local_ssh。  
4. **不要做**：模型直接拿私钥 ssh；不要默认自动生产；不要把图谱站 80/8000 与 ERP 预发端口混重启。

## 自测路径
