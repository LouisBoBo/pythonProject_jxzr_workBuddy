# 00 · 总览与架构分流

> **一句话**：ZR WorkBuddy 把「听懂人话、选工具、写说明」交给 Deep Agents 主环，把「真改文件 / 真提交 / 真发版」交给 local_dev / Cursor / git / SSH 旁路，中间用人点确认卡把关。  
> **不是**：模型回复里写「已提交 / 已部署 / 已导入」就算执行完——确认后由后端 API **直接**调工具或脚本，禁止「模型再说一遍确认」当执行。  
> **看图**：[流程图总览](./流程图总览.md)（总分流 + 各功能详图）

---

## 1. 实现原理

### 1.1 我们到底实现了什么？

大模型擅长理解与编排，但不适合当唯一执行者去灌 MES、改源码、`git push`、SSH 发版。若「模型觉得可以就动手」，会出现假执行（嘴上说做了）或越权执行（人没看清就改生产）。

所以定死：**聊天理解走主环；真动手走旁路；人点确认卡 → API 直执。**

| 人配的 / 人点的 | 系统干的 | 达到的效果 |
|----------------|----------|------------|
| 自然语言提问 | Deep Agents + Tools + Skills 理解、查数、讨论 | 对话里把事说清楚 |
| 上传文件说「导入」 | Middleware 挂 pending + 预览卡 | 未确认前 MES 无写入 |
| 确认卡上点确认 | API 直调同一段 Python / git / SSH | 可审计、可复现，不经模型二次 tool_call |
| 「提交本批」「部署到预发」 | `chatIntent` 旁路 prepare → 确认卡 → 真命令 | 高风险不进 Agent 当执行器 |
| 侧栏配自动化任务 | 调度器到点叫醒 Agent（功能 11） | 定时查/搜/整理，仍禁自动写码发版 |

**技术落点（整包）：**

| 层次 | 路径 |
|------|------|
| 前端意图 | `apps/web/src/chatIntent.js`、`ChatView.vue` |
| HTTP 对话 | `apps/api/routes/chat.py` → `POST /api/chat/stream` |
| 车道解析 | `apps/api/workbuddy_lanes.py`、`agent_lane_message.py` |
| Agent 编排 | `apps/api/agent_wrapper.py`（`AgentRunner`）→ `apps/agent/agents/agent.py`（`create_deep_agent`） |
| Middleware | `WriteConfirmMiddleware`、`HostPathGuardMiddleware`、`EntityGuardMiddleware` 等 |
| 并发 | `apps/api/stream_concurrency.py` |
| 写码旁路 | `apps/local_dev/`、`apps/cursor_dev/` |
| 定时任务 | `apps/automations/`（见功能 11） |
| Checkpoint | `data/agent_checkpoints.sqlite` |

### 1.2 和「一条消息全包办」差在哪？

| | **主对话环** | **旁路执行** |
|--|--------------|--------------|
| 谁发起 | 你打字进 SSE | 意图命中后走 prepare/Job/部署 API，或人点确认卡 |
| 谁干活 | Deep Agents（模型 + Tools + Skills） | `local_dev` / `cursor_dev` + git / SSH / GitHub API |
| 会不会真改盘 | 读为主；写 MES 先被拦成 pending | **会**，但必须人先确认 |
| 失败表现 | 聊天气泡 / tool 错误 | Job 状态、确认卡日志、审计记录 |

可以记成：**参谋在会议室出方案，施工队进车间干活**——会议室里不直接拧螺丝。

**技术上怎么隔开：**

| 点 | 实现 |
|----|------|
| 发送前分流 | `ChatView.send` 按固定顺序调 `chatIntent.js`，命中则旁路或带 `workbuddy_lane` |
| 车道互斥 | `page_context.workbuddy_lane` → `resolve_workbuddy_lane` / `sanitize_page_context_lanes` |
| 写提议拦截 | `WriteConfirmMiddleware` 截 `WRITE_TOOLS`（仅 `import_file_to_platform`）→ pending |
| 路径 / 实体守卫 | `HostPathGuardMiddleware`（拦本机绝对路径误读）；`EntityGuardMiddleware`（默认关，防问 A 查 B） |
| 确认后直执 | `writes.py` / `commit-batch` / `deploy` confirm：**不**再让模型二次 tool_call |

### 1.3 为什么确认卡后还要「API 直执」？

**人话：**  
若确认后再问模型「请执行」，模型可能答不一致，或嘴上说执行了实际没跑命令。把执行权钉在 FastAPI / 旁路服务上，人和审计才能对上「谁在什么时候真改了什么」。

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 写确认 | `POST /api/writes/actions/{id}/confirm` | `claim_action` → 同函数 `import_file_to_platform` |
| 提交 / 部署 | `local_dev` confirm 路由 | `git_commit` / `deploy_local_ssh` / `deploy_github` 在线程里跑 |
| 写码落地 | Job API | Cursor SDK / local_dev，不经 Deep Agents 当施工队 |
| 架构锁定 | `.cursor/rules/agent-harness-deep-agents.mdc` | 主 harness = Deep Agents；写码旁路 = Cursor |

### 1.4 端到端能力对照（按功能编号）

| 编号 | 能力 | 车道 / 路径 | 关键落点 |
|------|------|-------------|----------|
| 01 | PCB 专业对话 | 默认 SSE | `pcb-domain-chat` Skill |
| 02 | MES 查数 / 导出 / 分析 | 默认 SSE | `query_platform_data` 等 → `platform_api.py` |
| 03 | 文件导入 | SSE + confirm | `WriteConfirmMiddleware` + `writes.py` |
| 04 | 表结构摸底 | 默认 SSE | `schema_tool/*` |
| 05 | API 健康分析 | 默认 SSE | `api_log_tool/*` |
| 06 | 粘贴代码分析 | `paste_code` | 无 Git/IDE 全仓工具 |
| 07 | 代码审核 | `code_review` | IDE/Git 审码 Tools |
| 08 | 写码改功能 | `code_dev` + Job | `local_dev` / `cursor_dev` |
| 09 | 人触发提交 | 旁路 | `commit-batch` prepare → confirm |
| 10 | 人触发预发部署 | 旁路 | `deploy` prepare → confirm |
| 11 | 自动化任务 | 调度 + Deep Agents（独立 thread） | `apps/automations/*` → 企微/飞书 |

### 1.5 安全上钉死了什么？

| 约束 | 技术实现 |
|------|----------|
| 模型说完 ≠ 已执行 | 确认卡 → API 直执；禁止模型二次确认当执行 |
| 写码 / 审码 / 贴码互斥 | `workbuddy_lane` + ChatView 发送优先级 |
| 同会话单流 | `try_acquire_stream_lock`（`stream_concurrency.py`） |
| 本机路径误读 | `HostPathGuardMiddleware` |
| 写 MES 须人确认 | `REQUIRE_WRITE_CONFIRM` + `WRITE_TOOLS` |
| 配置热更新 | 设置页 → `data/settings.json` + `settings_store` |

## 2. 实现流程（人话 + 技术点怎么落地）

> 每节先讲「人看到什么 / 为什么这样」，再给 **技术点表** 和调用链。总览不重复各分册细节，只钉「发送后走哪条链」。

### 2.1 人打字发送后，前端怎么分流？

**人话：** 点发送时，ChatView 按固定优先级判断：部署、批提交、贴码、仅贴仓库 URL（先澄清）、审码、写码讨论；都不命中才走默认 SSE。同句多意图只走最高优先级，避免一条消息开两条危险链路。

```text
ChatView.vue send()
  ├─ looksLikeDeploy              → beginLocalDeploy（旁路，不进 Agent）
  ├─ looksLikeLocalCommitBatch    → beginLocalCommitBatch（旁路）
  ├─ looksLikePasteCodeAnalyze    → SSE + workbuddy_lane=paste_code
  ├─ isBareGitRepoUrlMessage      → 本地澄清气泡（写码 vs 审核），不自动开审/开写
  ├─ looksLikeGitRepoReview / looksLikeCodeReview
  │                                 → 审码选源 / SSE + lane=code_review
  ├─ shouldUseCodingDiscuss / looksLikeCodeDevIntent
  │                                 → 写码讨论 SSE + lane=code_dev（落地另走 Job）
  └─ 默认                          → POST /api/chat/stream（无专用 lane）
```

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 意图函数 | `chatIntent.js` | `looksLikeDeploy`、`looksLikeLocalCommitBatch`、`looksLikePasteCodeAnalyze`、`looksLikeCodeReview` / `looksLikeGitRepoReview`、`looksLikeCodeDevIntent` 等 |
| 优先级 | `ChatView.send` 顺序 | 部署 > 提交批 > 贴码 > 裸 URL 澄清 > 审码 > 写码 > 默认 SSE |
| 车道入参 | `page_context.workbuddy_lane` | 前端显式传入，后端 `sanitize_page_context_lanes` 丢非法值 |

---

### 2.2 默认 / 带车道的主对话环怎么跑？

**人话：** 请求进 FastAPI，鉴权后解析车道、抢同会话流锁，拼系统提示与 Skills，用 Deep Agents（LangGraph）流式推理；需要确认写入时 SSE 推确认卡，图表则推图表/看板结构。

```text
POST /api/chat/stream（routes/chat.py）
  → require_auth(JWT)
  → sanitize_page_context_lanes(page_context)     # workbuddy_lanes.py
  → AgentRunner.stream_chat（agent_wrapper.py）
       ├─ try_acquire_stream_lock(...)            # stream_concurrency.py
       ├─ build_system_prompt / lane 前缀         # entity_catalog + agent_lane_message
       ├─ create_agent() → create_deep_agent      # agent.py + skills/ + middleware
       └─ LangGraph checkpoint → data/agent_checkpoints.sqlite
  → SSE：token / tool_status / confirm / chart / dashboard / done
  → ChatView 渲染气泡、WriteConfirmCard、AnalysisChartCard 等
```

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 车道解析 | `resolve_workbuddy_lane` | 合法值：`code_dev` / `code_review` / `paste_code`；优先显式 page_context |
| Agent 主环 | `create_deep_agent` | Tools + Skills + Middleware + checkpointer |
| 写拦截 | `WriteConfirmMiddleware` | 截 `import_file_to_platform` → pending → SSE `confirm` |
| 路径守卫 | `HostPathGuardMiddleware` | 拦 `/Users/...` 等本机绝对路径误用 |
| 实体守卫 | `EntityGuardMiddleware` | 默认关；开启后拦明显选错实体的查询 |
| 模型 | `ChatOpenAI` + `LLM_*` / `DEEPSEEK_*` | DeepSeek 是**模型供应商**，不是框架 |
| 会话键 | 请求体 `thread_id` | Checkpoint / 历史按 **thread_id**，不是前端展示用的 session 别名混用 |

---

### 2.3 旁路执行（写码 / 提交 / 部署）怎么落地？

**人话：** 写码讨论可以在对话里谈；真改仓走 Job + Cursor。提交与部署发送前就被意图拦住，走 prepare → 确认卡 → 程序执行，模型不碰 git/ssh。

```text
写码落地：
  SSE 讨论 / :::cursor_dev_* 围栏
    → chatCursorDevParse.js
    → POST /api/local-dev/jobs 或 /api/cursor-dev/jobs
    → local_dev/service.py 或 cursor_dev（后台线程 + Cursor SDK）
    → data/local_dev_jobs/…

提交：
  looksLikeLocalCommitBatch
    → prepare_commit_batch → 确认卡 → confirm-commit
    → git_commit.commit_synced_files + _push_work_branch

部署：
  looksLikeDeploy
    → prepare_deploy → LocalDevDeployGateCard → confirm
    → deploy_local_ssh / deploy_github（线程）
```

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 硬约束 | confirm 后执行路径 | `git` / `ssh` / `rsync` / `workflow_dispatch` **不经**模型二次 tool_call |
| 与自动化区别 | 功能 11 | 时钟叫醒 Agent 做查/搜/整理；**禁止**任务里自动提交/部署 |

---

### 2.4 配置与资料从哪来？

**人话：** Key 和默认开关可以来自环境变量；日常改设置页并「保存并热更新」写入 `settings.json`；厂别资料包在 `mes_profiles`；写确认 pending 有 TTL。

```text
.env / 启动脚本          → LLM_*、部分开关默认值
设置页保存并热更新
  → settings_store → data/settings.json
MES 资料包
  → data/mes_profiles/{MES_PROFILE_ID}/（openapi、entities.json…）
写 pending
  → data/writes/pending/（TTL = WRITE_CONFIRM_TTL_SEC）
Checkpoint
  → data/agent_checkpoints.sqlite
```

**技术点：**

| 点 | 怎么做的 |
|----|----------|
| 热更新 | 须写入 `settings.json` 并触发热更新，否则进程仍读旧值 |
| 厂别 | `MES_PROFILE_ID` 决定激活哪套实体目录 |
| 写确认过期 | `WRITE_CONFIRM_TTL_SEC`（默认 1800） |

---

### 2.5 出问题时先查哪？

| 现象 | 人话原因 | 技术上先看 |
|------|----------|------------|
| 说了部署却进聊天 | 意图没命中或被贴码围栏挡住 | `looksLikeDeploy`；`ChatView.send` 顺序 |
| 写码和审码混卡 | 同句抢车道或 page_context 脏 | `workbuddy_lane`；`sanitize_page_context_lanes` |
| 设置改了不生效 | 没保存热更新 | `data/settings.json`；`settings_store` |
| 同会话两条流打架 | 锁被占 | `try_acquire_stream_lock` → `stream_busy` |
| 模型说「已导入」但库没有 | 未点确认卡或确认失败 | pending / `GET /api/writes/audit` |

## 4. 后续可以怎么做、不要做什么

**可以做：**

1. 继续加业务能力：优先新 Tool + Skill + Middleware，不新开 Agent 框架  
2. 高风险写一律确认卡 → API 直执  
3. 工程债：拆大 `ChatView.vue`、意图从正则更多落到显式 `lane`  

**不要做：**

1. 用 DeepSeek Harness / `dsh web` 换掉主对话壳  
2. 让模型直接 ssh/kubectl 改生产，或「模型二次确认」当执行  
3. 把写码 / 自动提交 / 自动发版塞回 Deep Agents 主环当默认真执行

## 自测路径（验收）

1. 普通问句 → 走 SSE，有流式回复。  
2. 「部署到预发」类话术 → 出现部署确认卡，**不**先进普通闲聊当执行。  
3. 「提交本批」→ 提交门禁卡，不经 Agent 当 git 执行器。  
4. 同会话连发两条流 → 第二条应 busy，第一条不断。  
5. 导入话术 → 出确认卡；未确认 MES 无写入（详见功能 03）。
