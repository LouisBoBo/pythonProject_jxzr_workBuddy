# 00 · 总览与架构分流

> 先搞懂这一篇，再看后面 10 个功能，不会把「聊天里的模型」和「真改文件 / 真发版」混在一起。

---

## 1. 实现原理

### 1.1 一句话

WorkBuddy 把「**聊天理解**」和「**真动手改东西**」拆开：前者走大模型主环，后者走后台程序旁路，中间用**确认卡**把人卡在环上。

### 1.2 为什么要拆两条车道？

大模型擅长听懂人话、选工具、写说明，但**不适合**当唯一执行者去做这些事：

- 往 MES 里灌数据（写错了难回滚）
- 改本机 / GitHub 上的源码（要可审计、可复现）
- `git push`、SSH 发版（权限大、误操作代价高）

如果让模型「自己觉得可以就执行」，常见两类事故：

1. **假执行**：回复里写「已提交 / 已部署」，其实没跑任何命令。  
2. **越权执行**：模型自己拼 SSH、改生产，人没看清就出事。

所以项目定死一条规则（见 `.cursor/rules/agent-harness-deep-agents.mdc`）：

> **人点确认卡 → 后端 API 直接调工具 / 调 Cursor / 调 git / 调部署脚本**  
> 不让模型在确认后再「口头确认一次」当执行。

### 1.3 两条车道分别干什么？

| 车道 | 典型功能 | 谁在工作 | 会不会真改文件/库 |
|------|----------|----------|-------------------|
| **主对话环** | PCB 答疑、查数、摸底、贴码讨论、审码编排、写码**讨论** | Deep Agents（模型 + Tools + Skills） | 读为主；写 MES 会先被 Middleware 拦成「待确认」 |
| **旁路执行** | 写码落地、批提交、预发部署 | `local_dev` / `cursor_dev` + git / SSH / GitHub API | **会**，但必须人先确认 |

可以把它想成：**参谋在会议室出方案，施工队进车间干活**——会议室里不直接拧螺丝。

### 1.4 前端怎么知道走哪条路？

`apps/web/src/chatIntent.js` 用关键词和上下文判断用户意图，**发送前**就决定：

- 走普通 SSE 对话（进 Agent）
- 还是直接打 `commit-batch` / `deploy` API（可不进 Agent）
- 还是带上 `workbuddy_lane`（`code_dev` / `code_review` / `paste_code`）

`workbuddy_lane` 由前端放进 `page_context`，后端 `workbuddy_lanes.py` 解析，避免「写码」和「审码」在同一句里抢路由。

### 1.5 配置从哪来？

- **环境变量**：`.env` / 启动脚本（如 LLM Key、默认开关）  
- **设置页**：`data/settings.json`，改完要点「保存并热更新」才落盘  
- **资料包**：`data/mes_profiles/{厂}/`（表结构、OpenAPI、生成的 `entities.json`）

## 2. 实现流程（技术点怎么落地）

> 下面按真实代码路径写。总览不重复各分册细节，只把「发送后走哪条链」钉死。

### 2.1 前端意图分流：`chatIntent.js` 在发请求前决策

```text
ChatView.vue send()
  → 依次调用 looksLikeDeploy / looksLikeLocalCommitBatch
    / looksLikePasteCodeAnalyze / looksLikeCodeReview / looksLikeCodeDevIntent
  → 命中则旁路 API 或附带 lane；都不命中 → 默认 SSE
```

| 意图 | 函数 | 典型去向 | 是否进 Agent |
|------|------|----------|--------------|
| 部署 | `looksLikeDeploy` | `POST /api/local-dev/deploy/prepare` | **否** |
| 批提交 | `looksLikeLocalCommitBatch` | `POST /api/local-dev/commit-batch/prepare` | **否**（门禁可局部调模型） |
| 贴码 | `looksLikePasteCodeAnalyze` | SSE + `lane=paste_code` | 是 |
| 审码 | `looksLikeCodeReview` | SSE + `lane=code_review` | 是 |
| 写码 | `looksLikeCodeDevIntent` | SSE + `lane=code_dev` → 后再 Job API | 讨论段是 |
| 其它 | — | `POST /api/chat/stream` | 是 |

**互斥规则：** 部署 > 提交批 > 贴码 > 审码 > 写码；同句多意图只走优先级最高的一条，防一条消息开两条危险链路。

### 2.2 主对话环（Deep Agents）

```text
POST /api/chat/stream（routes/chat.py）
  require_auth(JWT)
  sanitize_page_context_lanes(page_context)   # workbuddy_lanes.py
  AgentRunner.stream_chat（agent_wrapper.py）
    ├─ try_acquire_stream_lock(session_id)    # 同会话单流
    ├─ build_system_prompt(entity_catalog)    # 能力边界 + 车道说明
    ├─ create_agent() → create_deep_agent     # agent.py + skills/
    └─ LangGraph checkpoint（data/agent_checkpoints.sqlite）

SSE 回推：token / tool_status / confirm(write) / dashboard
ChatView 渲染消息、图表卡、WriteConfirmCard
```

| 技术点 | 实现 |
|--------|------|
| 车道解析 | `resolve_workbuddy_lane(message, page_context)`；合法值 `code_dev` / `code_review` / `paste_code` |
| 写提议拦截 | `WriteConfirmMiddleware` 截 `import_file_to_platform` → pending → SSE confirm |
| 模型供应商 | `ChatOpenAI` 兼容 `LLM_*` / `DEEPSEEK_*`；DeepSeek 是模型不是框架 |

### 2.3 旁路执行（local_dev / cursor_dev）

```text
写码：SSE 输出 :::cursor_dev_* 围栏
  → chatCursorDevParse.js 解析
  → POST /api/local-dev/jobs 或 /api/cursor-dev/jobs
  → service.py 后台线程 + Cursor SDK
  → job 文件 data/local_dev_jobs/…

提交：prepare_commit_batch → commit_gate → confirm-commit
  → git_commit.commit_synced_files + _push_work_branch

部署：prepare_deploy → LocalDevDeployGateCard → confirm
  → deploy_local_ssh / deploy_github（线程）
```

**硬约束：** 确认后的 `git` / `ssh` / `rsync` / `workflow_dispatch` **不经模型二次 tool_call**。

### 2.4 配置与资料包

| 来源 | 路径 / 模块 | 备注 |
|------|-------------|------|
| 环境变量 | `.env`、启动脚本 | LLM Key、默认开关 |
| 设置页 | `data/settings.json` | 须「保存并热更新」；`settings_store.py` |
| MES 资料包 | `data/mes_profiles/{id}/` | schema、openapi、entities.json |
| 写 pending | `data/writes/pending/` | TTL `WRITE_CONFIRM_TTL_SEC` |
| API 探活日志 | `DATA_DIR/api_calls/` | 健康分析与 ERP 出站共用存储 |

### 2.5 端到端对照（按功能编号）

| 编号 | 车道 | 关键 API / 模块 |
|------|------|-----------------|
| 01 PCB | 默认 SSE | `pcb-domain-chat` Skill |
| 02 查数 | 默认 SSE | `query_platform_data` → `platform_api.py` |
| 03 导入 | SSE + confirm | `writes.py` / `write_confirm.py` |
| 04 摸底 | 默认 SSE | `schema_tool/*` |
| 05 API 健康 | 默认 SSE | `api_log_tool/*` + sandbox |
| 06 贴码 | `paste_code` | 无 Git/IDE 工具 |
| 07 审码 | `code_review` | `ide_review/tool.py` |
| 08 写码 | `code_dev` + Job | `local_dev/service.py` |
| 09 提交 | 旁路 | `batch_commit.py` |
| 10 部署 | 旁路 | `deploy_prepare.py` |

### 2.6 常见排查

| 现象 | 查什么 |
|------|--------|
| 说了部署却进聊天 | `looksLikeDeploy` 是否命中；ChatView 发送顺序 |
| 写码和审码混卡 | `page_context.workbuddy_lane`；`agent.py` 车道提示块 |
| 设置改了不生效 | 是否写入 `settings.json` 并热更新 |
| 同会话两条流打架 | `try_acquire_stream_lock` 返回 busy |

## 3. 技术及用法

| 技术 | 在项目里怎么用 |
|------|----------------|
| **Vue 3 + Vite + Element Plus** | `apps/web`：对话页、设置页、各种确认卡 |
| **FastAPI + Uvicorn** | `apps/api`：登录、SSE 对话、写确认、写码/提交/部署 API |
| **Deep Agents + LangGraph** | `apps/agent/agents/agent.py` 的 `create_deep_agent`：主对话 |
| **ChatOpenAI 兼容接口** | 接 DeepSeek 等（`LLM_*` / `DEEPSEEK_*`），DeepSeek 是**模型供应商**不是框架 |
| **Skills（SKILL.md）** | `apps/agent/skills/*`：给模型的「剧本」（何时用何工具、禁止事项） |
| **Tools（Python 函数）** | `apps/agent/tools/*`：查 MES、摸底、探活、读 Git 文件等 |
| **Middleware** | `apps/agent/middleware/*`：写确认拦截、路径守卫、审计等 |
| **Cursor SDK** | 本机写码 `apps/local_dev/cursor_local_agent.py`；Cloud `apps/cursor_dev/` |
| **git / rsync / SSH / GitHub API** | 提交与部署旁路，在 `apps/local_dev/git_commit.py`、`deploy_*.py` |

配置：环境变量 + `data/settings.json`（设置页「保存并热更新」），见 `apps/agent/settings_store.py`、`apps/api/routes/settings.py`。

## 4. 后续扩展与优化建议

1. **继续加业务能力**：优先新 Tool + Skill，不要新开一套 Agent 框架。  
2. **高风险写**：一律确认卡 → API 直执，禁止「让模型再确认一次当执行」。  
3. **工程债**（阶段总评）：拆 `ChatView.vue`、给仓库自身加 CI、意图从正则更多落到显式 `lane`。  
4. **不要做**：用 DeepSeek Harness 换掉主对话壳；模型直接 ssh/kubectl 改生产。
