# 09 · 人触发提交（批审门禁 + 推送）

> 用户说「提交今天的代码」→ **只审本批改动** → 确认卡 → 工作分支 `commit`（默认可 `push`）。不是全仓审码车道，也不是写码收尾自动弹卡。

---

## 1. 实现原理

### 1.1 为什么一定要「人喊一声」才提交？

真实开发是：Cursor 改了很多轮，中间可能半拉子、可能还要本地跑一下。  
如果写码 Job 一结束就自动 `git commit`，会把未验证的改动推上去，也不符合「批」的概念。

所以产品设计是：

- **默认** `LOCAL_DEV_COMMIT_GATE=0`：写码结束**不**自动弹提交卡  
- 只有用户说「提交今天的代码」「提交本批」等，才走提交批链路

### 1.2 「本批」到底是哪些文件？

不是 IDE 里看到的所有 Changes，而是两道集合的交集（再加兜底）：

```text
A = 今天（日历日）内、已成功完成的 local_dev 写码 Job 记录下来的 synced_files
B = 当前 Git 工作区 git status --porcelain 里待提交的路径
待提交本批 ≈ A ∩ B（再过滤日志、.vite、node_modules 等噪音）
```

若 A 和 B 对不上（例如手改的文件没在同步池里），有 **git_dirty_fallback**：在仍是 git 仓的前提下，把业务源码类的脏文件纳入，但仍排除 `.dev-logs` 等。

**技术细节**：解析 porcelain 时不能对整段 stdout `.strip()`，否则首行 ` M backend/foo.py` 会变成 `M backend/...`，路径从第 4 个字符截取就得到 `ackend/...`——这是已修过的真实 bug。

### 1.3 门禁审什么？和全仓审码有何不同？

| 项目 | 全仓审码（功能 07） | 提交批审（本篇） |
|------|---------------------|------------------|
| 范围 | 用户指定的仓/工程 | **仅本批文件** |
| 触发 | 「审核仓库」 | 「提交今天的代码」 |
| 之后 | 出报告 | commit + 可选 push |
| 实现 | SSE + Agent 多轮读仓 | `batch_commit` + `commit_gate` API |

门禁层：`commit_gate.py` 规则（硬编码密钥、明显危险模式等）+ 可选 `commit_batch_review`（Skill/模型加深，可关）。

有 **P0 阻断** 或严重项时默认不让提交；`LOCAL_DEV_COMMIT_ALLOW_BLOCKED` 可放开（一般不推荐生产开）。

### 1.4 提交与推送分开设计

- **commit**：本地 `git add` + `git commit`，中文 message 必填（4～200 字、须含中文）  
- **push**：推到远程工作分支（如 `hebo`），可在确认卡填远程 URL  
- **push 失败**：本地 commit **保留**；确认卡进入 `push_retry` 模式，只重试 push，**不**重新 commit、**不**把 git 错误塞进 commit message

推送失败还会区分：

- **网络超时** → 提示修网络  
- **远程有新提交（fetch first）** → 自动 `fetch + rebase` 再推，或提示先拉取（非网络问题）

### 1.5 这条链路可以不经过大模型

`looksLikeLocalCommitBatch` 命中后，前端直接调 `local-dev` API，**不必**再走 `/api/chat/stream`。  
审门禁时可能调模型做批审，但 `git commit` / `git push` 一定是 Python 调 git，不是模型执行。

## 2. 实现流程（技术点怎么落地）

> 与部署类似：**意图旁路 → prepare 汇批+门禁 → confirm API 直调 git**。模型不参与 `git commit`。

### 2.1 意图识别：绕过 Agent

```text
looksLikeLocalCommitBatch(text) === true
  → 与 looksLikeDeploy 互斥（部署优先）
  → 与 MES「提交工单」等业务词区分（chatIntent 内 _looksLikeCommitCore）
  → POST /api/local-dev/commit-batch/prepare
     或 commit-batch（一步起 job）
  → 不走 POST /api/chat/stream
```

### 2.2 prepare：汇批文件 + 门禁

```text
prepare_commit_batch()（batch_commit.py）
  1. 当日 succeeded 的 local_dev jobs → collect synced_files（集合 A）
  2. git status --porcelain → 待提交路径（集合 B）
  3. filter_pending_commit_files：A ∩ B，去 .vite/node_modules/.dev-logs 等
  4. git_dirty_fallback：A∩B 空时，业务源码类脏文件兜底（仍过滤噪音）
  5. run_commit_review_gate(files)（commit_gate.py）
       - 规则：硬编码密钥、危险模式等
       - 可选 run_commit_batch_skill_review（Skill commit-batch-review）
  6. 返回 commit_gate 对象 + draft_chinese_commit_message
  7. job status = awaiting_commit
```

| 技术点 | 实现 |
|--------|------|
| porcelain 解析 | **不能**对整段 stdout `.strip()`，否则 ` M foo` → 路径截错 `ackend/...`（已修） |
| P0 阻断 | `blocking_count > 0` 默认不可提交 |
| 放开阻断 | `LOCAL_DEV_COMMIT_ALLOW_BLOCKED`（一般不推荐） |

### 2.3 前端确认卡

```text
LocalDevCommitGateCard.vue 展示：
  - 本批文件列表
  - 门禁 findings / verdict
  - 中文说明（4～200 字、须含中文）
  - 是否推送、远程 URL（可选）
```

### 2.4 confirm-commit：commit + push

```text
POST /api/local-dev/jobs/{job_id}/confirm-commit
  → finalize_commit_batch()（batch_commit.py）
  → validate_chinese_commit_message()
  → git_commit.commit_synced_files()
       - 禁止 main/master 等保护分支（LOCAL_DEV_WORK_BRANCH）
       - git add 本批路径 + git commit -m

  若勾选推送：
  → _push_work_branch()
       - git push -u origin {branch}
       - non-fast-forward → fetch + rebase → 再 push
       - 失败：push_retry=true，job 保持 awaiting_commit
       - humanize_push_error() 区分网络 / fetch-first / 鉴权
```

| 技术点 | 实现 |
|--------|------|
| push 失败保留 commit | 本地 sha 仍在；不污染 commit message |
| 仅重试推送 | `is_push_retry_needed` → 跳过门禁与 re-commit |
| 配置 | `LOCAL_DEV_COMMIT_PUSH`、`LOCAL_DEV_WORK_BRANCH` |

### 2.5 与写码 / 部署衔接

```text
local_dev Job succeeded（synced_files 已记）
  → 用户：「提交今天的代码」→ 本篇
  → push 成功
  → 用户：「部署到预发」→ prepare_deploy（功能 10）
```

默认 `LOCAL_DEV_COMMIT_GATE=0`：写码结束**不**自动弹提交卡。

### 2.6 常见排查

| 现象 | 查什么 |
|------|--------|
| 有改动但 0 文件 | A∩B 为空；fallback；job 是否 succeeded |
| 说明校验失败 | 无中文、超长；是否误拼 push 错误进 message |
| 推送失败只说修网络 | 是否实为 non-fast-forward（应 rebase 提示） |
| 保护分支拒绝 | `LOCAL_DEV_WORK_BRANCH` 是否指向 main |
| 与全仓审码混淆 | 是否误走 `code_review` SSE |

## 3. 技术及用法

| 技术 / 模块 | 怎么用 |
|-------------|--------|
| `chatIntent.js` `looksLikeLocalCommitBatch` | 意图拦截 |
| `batch_commit.py` | 汇批、门禁编排、finalize、push 重试 |
| `commit_gate.py` | 规则门禁 |
| `commit_batch_review.py` + Skill `commit-batch-review` | 可选加深审（可关模型调用） |
| `git_commit.py` | 分支策略、中文 message、porcelain 解析、push/rebase |
| `LocalDevCommitGateCard.vue` | 确认 / 重试推送 UI |
| 配置 | `LOCAL_DEV_COMMIT_GATE`、`LOCAL_DEV_COMMIT_PUSH`、`LOCAL_DEV_COMMIT_ALLOW_BLOCKED`、`LOCAL_DEV_COMMIT_USE_*_REVIEW`、`LOCAL_DEV_WORK_BRANCH` |

保护分支名（main/master 等）禁止当作工作分支乱提交。

## 4. 后续扩展与优化建议

1. **可做**：确认卡更清晰展示「本批 vs IDE Changes 面板」差异，减少「我明明改了却说没文件」。  
2. **可做**：rebase 冲突时给出可点击的本机命令提示。  
3. **P1-2 Cloud PR** 已跳过；不要和本机提交批混成一条车道。  
4. **不要做**：写码成功自动 commit；不要把全仓审码结果当成批审门禁。

---

## 自测路径

1. 本机写码改 1～2 个业务文件 → 「提交今天的代码」→ 卡上文件数合理。  
2. 阻断项存在时不能提交（除非显式允许）。  
3. 断网或远程超前：本地 commit 仍在，可「重试推送」；文案不应一律「修网络」。
