# 09 · 人触发提交（批审门禁 + 推送）

> **一句话**：你说「提交今天的代码」→ 系统只汇总**本批**改动 → 门禁审完出确认卡 → 你点确认后在工作分支 `commit`（默认可再 `push`）。  
> **不是**：全仓审码车道（功能 07）；也不是写码 Job 一结束就自动弹提交卡 / 自动 commit。  
> **看图**：[流程图总览 §6](./流程图总览.md#6-功能-09人触发提交两步-api别当成一步)

---

## 1. 实现原理

### 1.1 我们到底实现了什么？

Cursor 可能改了很多轮，中间半拉子、还要本地跑一下很常见。若写码一成功就 `git commit`，会把未验证的改动推上去，也不符合「本批」概念。  
所以做了 **人触发提交批**：只有你喊一声，才汇批 → 门禁 → 确认 → 程序调 git。

| 人做的 | 系统干的 | 达到的效果 |
|--------|----------|------------|
| 说「提交今天的代码 / 提交本批」 | 意图旁路，**不进** `/api/chat/stream` | 不靠模型「口头已提交」 |
| 看确认卡上的文件与门禁 | 只审本批文件，不是全仓 | 范围可控、可解释 |
| 填中文说明、是否推送 | `git add` + `commit`（+ 可选 `push`） | 本地有 commit；远程工作分支可更新 |
| push 失败后再点「重试推送」 | 只重试 push，**不**重新 commit | 本地 sha 保留，message 不被污染 |

**技术落点（整包）：**

| 层次 | 路径 |
|------|------|
| 业务包 | `apps/local_dev/`：`batch_commit.py`、`commit_gate.py`、`commit_batch_review.py`、`git_commit.py` |
| HTTP | `apps/api/routes/local_dev.py`（`/commit-batch/prepare`、`/commit-batch`、`/jobs/{id}/confirm-commit`） |
| 意图 | `apps/web/src/chatIntent.js`：`looksLikeLocalCommitBatch` + `rawLooksLikeDeploy` 互斥 |
| 确认卡 | `LocalDevCommitGateCard.vue` |
| 配置 | `LOCAL_DEV_COMMIT_GATE`、`LOCAL_DEV_COMMIT_PUSH`、`LOCAL_DEV_COMMIT_ALLOW_BLOCKED`、`LOCAL_DEV_COMMIT_USE_*_REVIEW`、`LOCAL_DEV_WORK_BRANCH` |

### 1.2 和「全仓审码」「写码收尾」差在哪？

| | 全仓审码（功能 07） | **提交批（本篇）** | 写码 Job 收尾 |
|--|---------------------|--------------------|---------------|
| 谁发起 | 「审核仓库」 | 「提交今天的代码」 | Job 成功（默认**不**弹卡） |
| 范围 | 用户指定的仓/工程 | **仅本批文件** | — |
| 之后 | 出报告 | commit + 可选 push | 仅记 `synced_files` |
| 实现 | SSE + Agent 多轮读仓 | `batch_commit` + `commit_gate` API | `LOCAL_DEV_COMMIT_GATE` 默认 0 |

**技术上怎么隔开：**

| 点 | 实现 |
|----|------|
| 意图互斥 | `looksLikeLocalCommitBatch` 内：`rawLooksLikeDeploy(t)` 为真则 **false**（部署优先） |
| 无 `_looksLikeCommitCore` | 提交匹配逻辑就在 `looksLikeLocalCommitBatch` 本体；部署核心是 `rawLooksLikeDeploy` |
| 业务「提交工单」 | 正则排除工单/审批/表单等，避免误走 git |
| 不进 SSE | ChatView 命中后直接 `prepareLocalDevCommitBatch` / `startLocalDevCommitBatch` |
| 默认不自动弹卡 | `LOCAL_DEV_COMMIT_GATE=0` |

### 1.3 「本批」到底是哪些文件？

**人话：** 不是 IDE Changes 面板里看到的全部，而是「今天写码同步过的」和「现在 git 还脏着的」的交集；对不上时还有脏文件兜底，但仍滤掉日志、`.vite`、`node_modules` 等噪音。

```text
A = 今日（日历日）succeeded 的 local_dev Job 记下的 synced_files
B = git status --porcelain 待提交路径
待提交本批 ≈ A ∩ B（再过滤噪音）
A∩B 空 → git_dirty_fallback：业务源码类脏文件（仍排除 .dev-logs 等）
```

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 汇批 | `collect_batch_synced_files` + `filter_pending_commit_files` | A∩B + 噪音过滤 |
| 兜底 | `git_dirty_fallback`（`git_commit.py`） | 仍要求是 git 仓 |
| porcelain 解析 | `git_commit` 读 porcelain | **不能**对整段 stdout `.strip()`，否则首行 ` M foo` 路径截成 `ackend/...`（**已修**） |

### 1.4 为什么 prepare 和门禁要拆开？

**人话：**  
- prepare 很快：先把「有哪些文件」亮出来，人知道系统在干活。  
- 门禁可能调规则 / Skill / 模型，稍慢，放在起 batch（`/commit-batch`）时再跑。

**关键约定（必记）：**

| 步骤 | API | 干什么 | **不**干什么 |
|------|-----|--------|--------------|
| prepare | `POST /api/local-dev/commit-batch/prepare` | **只**收集 / 过滤本批文件 | **不**跑门禁、**不**创建提交 Job |
| start | `POST /api/local-dev/commit-batch` | 跑 `run_commit_review_gate`、建 `awaiting_commit` Job | 此时才有门禁结果 |
| confirm | `POST /api/local-dev/jobs/{id}/confirm-commit` | 真 `git commit` / `push` | 模型不参与 git |

### 1.5 安全上钉死了什么？

| 约束 | 技术实现 |
|------|----------|
| 保护分支禁乱提交 | `LOCAL_DEV_WORK_BRANCH`；禁止当 main/master 工作分支乱 commit |
| P0 阻断默认不可提交 | `blocking_count > 0` → `can_commit=false` |
| 放开阻断须显式 | `LOCAL_DEV_COMMIT_ALLOW_BLOCKED`（生产一般不推荐） |
| 中文 message | `validate_chinese_commit_message`：4～200 字、须含中文 |
| push 失败不污染 message | `push_retry`；`humanize_push_error` 区分网络 / fetch-first / 鉴权 |
| git 由程序执行 | Python 调 git，不是模型拼命令 |

## 2. 实现流程（人话 + 技术点怎么落地）

> 每节先讲「人看到什么 / 为什么这样」，再给 **技术点表** 和调用链。

### 2.1 意图识别：为什么一句话不进 Agent？

**人话：** 「提交今天的代码」是开关 + 文件集合 + 确认问题，不需要大模型再理解一遍；也不希望模型幻觉「已提交」。发送前直接拦到 local-dev API。

```text
ChatView.vue send()
  → looksLikeLocalCommitBatch(text) === true
       ├─ rawLooksLikeDeploy(t) → 直接 false（部署优先）
       ├─ 排除「提交工单 / 审批」等业务词
       └─ 命中「提交今天的代码 / commit …」等
  → prepareLocalDevCommitBatch → POST …/commit-batch/prepare
  → startLocalDevCommitBatch → POST …/commit-batch
  → 不走 POST /api/chat/stream
```

**技术点：**

| 点 | 怎么做的 |
|----|----------|
| 导出函数 | `looksLikeLocalCommitBatch`（**没有** `_looksLikeCommitCore`） |
| 部署互斥 | 复用 `rawLooksLikeDeploy`，与 `looksLikeDeploy` 同源 |
| 写码互斥 | 有明确写码动作词且无「提交」→ 不走本链路 |

---

### 2.2 prepare：只汇批，零门禁

**人话：** 先快速算出本批文件列表（或「同步池都已提交」），前端可先展示进度/预览；**此步不做审码门禁、不创建 Job**。

```text
POST /api/local-dev/commit-batch/prepare
  → prepare_commit_batch(...)（batch_commit.py）
       1. collect_batch_synced_files（今日 succeeded jobs → synced_files）
       2. 今日为空可放宽到非 today_only 再试一次
       3. filter_pending_commit_files：A ∩ B，去噪音
       4. 返回 files / preview / batch 元数据
       ※ 不调用 run_commit_review_gate
       ※ 不创建 awaiting_commit Job
```

**技术点：**

| 点 | 函数 | 怎么做的 |
|----|------|----------|
| 只收集 | `prepare_commit_batch` | 文档字符串写明「仅汇总本批文件（快）」 |
| 空文件 | `pending=false` | 可能已本地提交；仍可后续仅 push |

---

### 2.3 start：门禁 + 建确认 Job

**人话：** 第二步才真正审本批、起草中文说明、建一张待确认卡。若已有未确认的旧批，会被取代（skip），避免「丢卡死锁」。

```text
POST /api/local-dev/commit-batch
  → start_commit_batch(...)（batch_commit.py）
       ├─ 可带上 prepare 返回的 files；否则内部再 prepare 一次
       ├─ supersede_pending_commit_batches（旧 awaiting_commit → skip）
       ├─ run_commit_review_gate(files)（commit_gate.py）
       │     规则：硬编码密钥、危险模式等
       │     可选 commit_batch_review（Skill）/ ide_review
       ├─ draft_chinese_commit_message
       └─ job status = awaiting_commit，挂 commit_gate
```

**技术点：**

| 点 | 怎么做的 |
|----|----------|
| 门禁入口 | **仅** `start_commit_batch` / 等价直调 `/commit-batch` 时跑 gate |
| P0 | `blocking_count > 0` 默认不可提交 |
| 可选加深 | `LOCAL_DEV_COMMIT_USE_*_REVIEW`；Skill `commit-batch-review` |
| push 重试恢复 | 无新文件但有近期 push_retry Job → 直接恢复确认卡 |

---

### 2.4 确认卡：人看到什么？

**人话：** 卡上列出本批文件、门禁结论、中文说明输入框、是否推送与远程 URL。有阻断时不能提交（除非显式允许）。

```text
LocalDevCommitGateCard.vue
  - 本批文件列表
  - 门禁 findings / verdict
  - 中文说明（4～200 字、须含中文）
  - 是否推送、远程 URL（可选）
  - push_retry 模式：只重试推送
```

---

### 2.5 confirm-commit：真 commit + push

**人话：** 点确认 → 后端校验中文说明 → 工作分支上 `git add` 本批并 commit → 若勾选推送再 push。远程超前会尝试 fetch+rebase 再推；仍失败则本地 commit 保留，卡进入「重试推送」。

```text
POST /api/local-dev/jobs/{job_id}/confirm-commit
  → finalize_commit_batch(...)（batch_commit.py）
  → validate_chinese_commit_message()
  → git_commit.commit_synced_files()
       - 禁止 main/master 等保护分支乱当作工作分支
       - git add 本批 + git commit -m（中文）

  若勾选推送：
  → _push_work_branch()
       - git push -u origin {branch}
       - non-fast-forward → fetch + rebase → 再 push
       - 失败：push_retry=true，保持 awaiting_commit
       - humanize_push_error()：网络 / fetch-first / 鉴权
```

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 直执 git | `finalize_commit_batch` | 不经 `run_job` / 模型 |
| 仅重试推送 | `is_push_retry_needed` | 跳过门禁与 re-commit |
| 配置 | `LOCAL_DEV_COMMIT_PUSH`、`LOCAL_DEV_WORK_BRANCH` | 默认是否推、工作分支名 |

---

### 2.6 与写码 / 部署衔接

```text
local_dev Job succeeded（synced_files 已记）
  → 用户：「提交今天的代码」→ 本篇
  → push 成功
  → 用户：「部署到预发」→ prepare_deploy（功能 10）
```

默认 `LOCAL_DEV_COMMIT_GATE=0`：写码结束**不**自动弹提交卡。

### 2.7 页面 / API 对照

| 你在对话里做的 | 前端 `api.js` | 后端路由 | 核心函数 |
|----------------|---------------|----------|----------|
| 说「提交今天的代码」 | `prepareLocalDevCommitBatch` | `POST /commit-batch/prepare` | `prepare_commit_batch`（**只汇批**） |
| 进入门禁 / 出卡 | `startLocalDevCommitBatch` | `POST /commit-batch` | `start_commit_batch` + `run_commit_review_gate` |
| 点确认提交 | `confirmLocalDevCommit` | `POST /jobs/{id}/confirm-commit` | `finalize_commit_batch` |

均需登录；OpenAPI tags 中文（本机写码相关），summary 为中文。

### 2.8 从头到尾一眼版

```text
【意图】looksLikeLocalCommitBatch（与 rawLooksLikeDeploy 互斥）
        ↓
【prepare】只收集 A∩B / fallback 文件列表
        ↓
【start】run_commit_review_gate → awaiting_commit Job
        ↓
【确认卡】LocalDevCommitGateCard
        ↓
【confirm】中文 message → commit → 可选 push（失败则 push_retry）
        ↓
【下一步】人触发功能 10 部署
```

---

### 2.9 出问题时先查哪？

| 现象 | 人话原因 | 技术上先看 |
|------|----------|------------|
| 有改动但 0 文件 | A∩B 空；job 未 succeeded；工作区路径不一致 | prepare 返回的 `batch` / `synced_pool`；`git_dirty_fallback` |
| 说明校验失败 | 无中文、超长；误把 push 错误拼进 message | `validate_chinese_commit_message` |
| 推送失败只说修网络 | 实为远程超前 | `humanize_push_error`；应出现 rebase / 先拉取提示 |
| 保护分支拒绝 | 工作分支指到 main | `LOCAL_DEV_WORK_BRANCH` |
| 与全仓审码混淆 | 误走 `code_review` SSE | 是否命中 `looksLikeLocalCommitBatch` |
| 以为 prepare 就会审 | 概念混了 | 门禁只在 `/commit-batch`（`start_commit_batch`） |

## 3. 技术及用法（速查）

| 模块 | 关键函数 | 干什么 |
|------|----------|--------|
| `chatIntent.js` | `looksLikeLocalCommitBatch`、`rawLooksLikeDeploy` | 意图拦截与部署互斥 |
| `batch_commit.py` | `prepare_commit_batch`、`start_commit_batch`、`finalize_commit_batch` | 汇批 / 门禁编排 / 确认执行 |
| `commit_gate.py` | `run_commit_review_gate` | 规则门禁 |
| `commit_batch_review.py` | Skill `commit-batch-review` | 可选加深审 |
| `git_commit.py` | porcelain、中文 message、push/rebase、`humanize_push_error` | 真 git |
| `LocalDevCommitGateCard.vue` | 确认 / 重试推送 UI | 人控 |

**配置：**

| 变量 | 含义 |
|------|------|
| `LOCAL_DEV_COMMIT_GATE` | 写码结束是否自动门禁（默认 **关**） |
| `LOCAL_DEV_COMMIT_PUSH` | 确认后是否默认尝试 push |
| `LOCAL_DEV_COMMIT_ALLOW_BLOCKED` | 是否允许带着阻断项提交 |
| `LOCAL_DEV_COMMIT_USE_*_REVIEW` | 是否启用 Skill / IDE 加深审 |
| `LOCAL_DEV_WORK_BRANCH` | 工作分支；勿指向 main/master |

## 4. 后续可以怎么做、不要做什么

**可以做：**

1. 确认卡更清晰展示「本批 vs IDE Changes」差异，减少「我明明改了却说没文件」  
2. rebase 冲突时给出可点击的本机命令提示  
3. Cloud PR 合入路径单独产品化（勿与本机提交批混成一条车道）  

**不要做：**

1. 写码成功自动 commit  
2. 把全仓审码结果当成批审门禁  
3. 把门禁塞回 `prepare_commit_batch`（prepare 必须保持「只收集」）  
4. 让模型执行 `git commit` / `git push`  

---

## 自测路径（验收）

1. 本机写码改 1～2 个业务文件 → 「提交今天的代码」→ prepare 有文件预览 → start 后门禁卡文件数合理。  
2. 阻断项存在时不能提交（除非显式允许）。  
3. 断网或远程超前：本地 commit 仍在，可「重试推送」；文案不应一律「修网络」。  
4. 再说「部署到预发」应走功能 10，不应与本卡混成一次自动发版。
