# 阶段收口：Codex 评审提示词 + 15 分钟验收清单

> 适用：`hebo` 上已合并的 ops 硬化（嵌入 / 写确认 UX / 实体话术 / HA 共享卷）。  
> 目的：AI 写得多时，用「外聘评审 + 可跑通验收」把关，不要求你读懂每一行。

---

## 一、给 `codex.review` / `cursor.review` 的提示词（复制即用）

在 Cursor 里启用 review MCP 后，把下面整段交给 Agent（或直接作为 `review_request`）：

```text
请对 WorkBuddy（simplified-workbuddy）本阶段 ops 硬化改动做只读安全与正确性评审。

【范围 · 优先文件】
- apps/agent/ha/fs_lock.py
- apps/agent/middleware/write_store.py
- apps/agent/middleware/write_confirm.py
- apps/api/routes/history.py
- apps/api/routes/chat.py（page_context / thread_id）
- apps/api/main.py（/health/ready、CORS）
- apps/web/src/embed.js
- apps/web/src/auth.js
- apps/web/src/App.vue（embed 布局）
- docker-compose.ha.yml、deploy/nginx-ha.conf

【对照基线】
- 相对分支：main（或合并前的 hebo 父提交亦可）
- 产品约束：查询/导入/写确认/API 健康主路径不应被破坏

【请重点回答】
1. 并发：InterProcessLock 是否可重入正确？多进程 claim_action 是否仍可能双写？
2. 权限：历史会话是否可能串用户？legacy 无主会话认领是否过宽？
3. 嵌入：URL 带 access_token 的泄露面（日志、referrer、本地存储）；去掉 query 是否足够？
4. 写确认：过期 / 410 / 审计 write_expired 是否一致？多 pending 是否互相覆盖？
5. HA：共享 DATA_DIR + flock 在 NFS 上的已知风险；compose 双实例实际能否防双确认？
6. 配置：CORS=*、AUTH_REQUIRED、默认线程 default 改写是否有坑？

【输出格式】
- 按严重度：P0（必须修）/ P1（建议修）/ P2（可选）
- 每条：文件路径 + 现象 + 为何危险 + 建议改法（一两句）
- 明确写出「未发现」的项，避免空泛 LGTM
- 不要修改代码，只要评审结论
```

跑完后：把 JSON/结论里的 **P0/P1** 丢回给写码 Agent：「按 P0/P1 修，P2 先记着」。

## 二、你本人 15 分钟验收清单（不必懂实现）

环境：`./scripts/dev.sh`（Web 5180 / API 8765）。Docker HA **不必**为这 15 分钟启动。

### A. 机器冒烟（约 3 分钟）

在仓库根目录：

```bash
make smoke-ha
make smoke-embed-identity
make smoke-entity-phrases
```

期望：均出现 `SMOKE_OK`。任一条 FAIL → 先别演示，把输出贴给 Agent。

### B. 登录与历史（约 3 分钟）

| # | 操作 | 期望 |
|---|------|------|
| 1 | ERP 账号登录进入对话 | 能进，侧栏有用户名 |
| 2 | 看左侧历史 | 以前的会话还在（不会空白） |
| 3 | 点开一条旧会话 | 消息能加载 |

失败含义：用户隔离/认领有问题。

### C. 写确认（约 5 分钟）

| # | 操作 | 期望 |
|---|------|------|
| 1 | 上传 CSV，要求导入工单 | 出现确认卡，**平台尚未多数据** |
| 2 | 看卡上倒计时 | 有「xx 后过期」 |
| 3 | 点「确认写入」 | 文案变为已确认写入；平台有数据（或 Mock 成功） |
| 4 | 点开「本会话写操作记录」 | 能看到待确认 → 已写入 |

失败含义：HITL / 审计 UX 回退。

### D. 查询实体边界（约 2 分钟）

| # | 操作 | 期望 |
|---|------|------|
| 1 | 「查排程计划」 | 结果是计划（plan_no 等），不是工单 WO |
| 2 | 「查 pending 工单」或「紧急工单」 | 会查工单且带筛选意识（或结果合理） |

失败含义：实体/话术选错实体。

### E. 三条「敢不敢用」问题（约 2 分钟，只回答是/否）

1. **谁能改平台数据？** → 只有确认卡点确认之后（未确认不应写入）  
2. **谁能看谁的历史？** → 当前登录用户自己的（不要用第二个号测串号，有空再测）  
3. **会不会误打生产？** → 文档探活默认沙箱；日常演示用 Mock 或明确测试 ERP  

三条都能答「符合预期」→ 本阶段可以演示/给实施试用。  
任一条心里没底 → 先跑 Codex 评审或让 Agent 对照代码讲清楚再往前。

## 三、可选：HA 彩排（另算时间，非每日必做）

```bash
docker compose -f docker-compose.ha.yml up -d --build --scale api=2
curl -s http://127.0.0.1:8765/health/ready
# 用完：
docker compose -f docker-compose.ha.yml down
```

期望：`status` 为 `ready`；两 api healthy。这只证明「双实例能起」，**不能替代**上面的写确认手工验收。

## 四、建议节奏

| 时机 | 做什么 |
|------|--------|
| 每次小改 | 相关 `make smoke-*` + 改动点手工 1～2 步 |
| 大 PR / 阶段收口 | 全文 15 分钟清单 + Codex 评审提示词 |
| 准备给别人演示 | 至少 B+C+E 过一遍 |
