# 07 · 代码审核

> 对**公开 Git 仓**或**本机 IDE 工程**做工程级审阅，按 P0/P1/P2 出中文「代码审核报告」。与写码车道对等、互不抢。

---

## 1. 实现原理

### 1.1 审码 = 只读体检，写码 = 动刀手术

代码审核要对**整仓或整个 IDE 工程**做结构化检查，输出带严重级别的中文报告（P0 阻断 / P1 重要 / P2 建议）。  
全程**只读**：不 `git commit`、不 Cursor 改文件、不部署。

和写码车道**对等、互斥**：前端 `workbuddy_lane=code_review` 时，禁止出现写码围栏 `:::cursor_dev_*`。

### 1.2 两条取码来源

| 来源 | 适用场景 | 代码怎么到 Agent 手里 |
|------|----------|------------------------|
| **Git 公开仓** | 有 HTTPS 地址、可浅克隆 | `git_review.py` 克隆/镜像 → 列文件 → 分批读内容 |
| **本机 IDE** | 工程在开发者电脑上 | VS Code 扩展读文件 → Bridge API 回传 |

Git 路径不依赖 VS Code；IDE 路径依赖扩展配对（`IDE_REVIEW_ENABLED` 控制是否注册 IDE 工具）。

### 1.3 为什么要「分批读」？

一个仓库几千个文件，不能一次全塞进模型上下文。  
`batch_plan.py` 按目录/业务源码过滤（`local_files.is_functional_source_rel`）→ 多轮 `read_batch` → 每批审完再汇总终稿。  
用户能在过程区看到「第几批 / 共几批」。

### 1.4 Skill 分层

| Skill | 作用 |
|-------|------|
| `code-review` | 方法论：什么叫 P0/P1/P2、报告结构 |
| `git-code-review` | Git 来源的步骤：list → read_batch → 终稿 |
| `ide-code-review` | IDE 来源的步骤 + Bridge 约定 |

### 1.5 和「提交批审」（功能 09）的区别

| 项目 | 全仓审码（本篇） | 提交批审 |
|------|------------------|----------|
| 触发 | 「审核这个仓库」 | 「提交今天的代码」 |
| 范围 | 用户选的仓/工程 | **仅本批同步的文件** |
| 之后 | 出报告 | 还要 git commit/push |
| API | 走 SSE + Agent | 走 `batch_commit` API |

共用部分审码规则/enrich，但**路由完全分开**。

## 2. 实现流程（技术点怎么落地）

> 审码走 **SSE + `code_review` lane + Git/IDE 只读工具**；与提交批 `batch_commit` API 完全分开。

### 2.1 意图与车道

```text
looksLikeCodeReview(text) 或 looksLikeGitRepoReview(text)
  → page_context.workbuddy_lane = 'code_review'
  → POST /api/chat/stream

agent.py 车道块：
  - 加载 code-review / git-code-review / ide-code-review Skill
  - 禁止 :::cursor_dev_*（写码围栏）
  - code_dev 车道则相反：禁止 request_git_* / request_ide_*
```

### 2.2 Git 仓审核链路

```text
用户：「审核 https://github.com/org/repo」
  → GitRepoPickCard 确认 URL、分支（前端）
  → 模型 tool_call:

request_git_list_source_files(repo_url, ref)
  → git_review.py 浅克隆到临时目录
  → local_files.is_functional_source_rel 过滤非业务文件
  → 返回相对路径列表

多轮 request_git_read_batch(paths[])
  → batch_plan.py 控制每批文件数
  → 每批内容进上下文；过程区显示「第 i/N 批」

终稿：## 🔍 代码审核报告
  → P0 / P1 / P2 分级（code-review Skill）
  → 任务结束清理临时克隆目录
```

| 技术点 | 实现 |
|--------|------|
| 私仓 | HTTPS 无 token 会克隆失败；须公开仓或后续扩展凭据 |
| 分批 | 避免一次塞全仓爆 token；`batch_plan` 按目录切批 |
| 增强 | `enrich.py` / `review.py` 统一严重级别与报告结构 |

### 2.3 本机 IDE 审核链路

```text
前置：vscode-workbuddy-bridge 扩展 + IdeBridgePairCard 配对
  → bridge_token 存 bridge_store.py

request_ide_list_source_files(workspace_root)
  → routes/ide_bridge.py 入队
  → extension.js 本机列文件 → poll/result 回传

request_ide_read_batch(paths[])
  → 同上 Bridge 往返

request_ide_review(...) 或模型按 Skill 直接写报告
```

| 技术点 | 实现 |
|--------|------|
| 开关 | `IDE_REVIEW_ENABLED` 控制是否注册 IDE 工具 |
| 配对 | `bridge_token.py`；过期须重新配对 |
| 安全 | Bridge 只读本机用户授权的工作区 |

### 2.4 与提交批审（功能 09）对照

| 项目 | 全仓审码（本篇） | 提交批审 |
|------|------------------|----------|
| 触发 | 「审核仓库」 | `looksLikeLocalCommitBatch` |
| API | `/api/chat/stream` | `/api/local-dev/commit-batch/*` |
| 范围 | 用户指定仓/工程 | 当日 Job `synced_files` ∩ git dirty |
| 之后 | 报告 | `git commit` + `push` |
| 模块 | `ide_review/tool.py` | `commit_gate.py` + `batch_commit.py` |

共用 `enrich` 规则词典，但**路由互斥**。

### 2.5 常见排查

| 现象 | 查什么 |
|------|--------|
| 克隆失败 | URL、私仓权限、网络 |
| IDE pending 卡住 | 扩展是否运行；`ide_bridge` poll 日志 |
| 同时弹写码卡 | `workbuddy_lane` 是否为 `code_dev` |
| 报告格式像贴码 | 是否误走 `paste_code` lane |

## 3. 技术及用法

| 技术 / 模块 | 怎么用 |
|-------------|--------|
| `ide_review/tool.py` | 注册 request_git_* / request_ide_* |
| `git_review.py` / `local_files.py` / `batch_plan.py` | 列表、分批、过滤业务源码 |
| `enrich.py` / `review.py` | 增强与报告结构 |
| `bridge_store.py` / `bridge_token.py` | 配对与任务队列 |
| Skills | `code-review`、`git-code-review`、`ide-code-review` |
| 前端卡 | `CodeReviewSourcePickCard`、`GitRepoPickCard`、`IdeWorkspacePickCard`、`IdeBridgePairCard` |
| 配置 | `IDE_REVIEW_ENABLED` |

注意：提交批审（功能 09）**复用部分审码能力**，但是独立 API 门禁，不是走「全仓审码车道」。

---

## 4. 后续扩展与优化建议

1. **可做**：报告结构化落库，方便「上次 P0 是否已修」。  
2. **可做**：与提交批门禁规则对齐同一套严重级别词典。  
3. **慎做**：一次读全仓无分批（token 与超时会爆；现有 batch 是有意的）。  
4. **不要做**：审核过程中调用写码 propose / 自动改仓。

---

## 自测路径

1. Git：给可访问 HTTPS 仓，应出带 P0/P1/P2 的报告。  
2. IDE：配对成功后审一小目录，过程区有分批，终稿有报告标题。  
3. 同一句勿同时触发写码卡。
