# 06 · 粘贴代码分析

> **一句话**：你在对话里贴一段源码围栏，问「有什么问题 / 怎么改」→ 系统走进 `paste_code` 车道，当场给问题列表和改写建议（短确认后贴完整代码）。  
> **不是**：全仓 / IDE 工程审核（功能 07），也不是写码 Job、自动提交或往磁盘写文件。

---

## 1. 实现原理

### 1.1 我们到底实现了什么？

工程师常在聊天里贴 20～200 行代码，只想让同事瞟一眼：「有啥 bug？怎么改？」  
不需要克隆仓库，也不需要开 VS Code Bridge。  
所以做了 **粘贴代码分析**：前端识别代码围栏 + 分析意图 → 强制 `workbuddy_lane=paste_code` → Deep Agents 只读消息里的代码块作答，交付全在聊天气泡里。

| 人做的 | 系统干的 | 达到的效果 |
|--------|----------|------------|
| 贴 ``` 代码 +「有什么问题」 | 识别贴码意图，注入贴码车道 | 不弹选仓卡 / 不弹写码卡 |
| 看问题与建议 | Skill + 专用系统提示约束输出形态 | 轻量、即时、只看眼前这一段 |
| 回「来吧 / 好的」 | 同会话续写，直接贴完整改后代码 | 不再开 PCB 科普或平台介绍 |

**技术落点（整包）：**

| 层次 | 路径 |
|------|------|
| 意图 | `apps/web/src/chatIntent.js`（`looksLikePasteCodeAnalyze` 等） |
| 发送顺序 | `ChatView.vue`（围栏挡住部署/提交误伤） |
| 车道 | `apps/api/workbuddy_lanes.py` → `LANE_PASTE_CODE` |
| 注入 | `apps/api/agent_lane_message.py`（`【路由·贴码】`） |
| 提示 | `apps/agent/agents/agent.py` → `_PASTE_CODE_ANALYZE_PROMPT` |
| Skill | `apps/agent/skills/paste-code-analyze/SKILL.md` |

### 1.2 和「审码」「写码」差在哪？

| | **贴码分析（本篇）** | 代码审核（功能 07） | 写码改功能（功能 08） |
|--|---------------------|---------------------|----------------------|
| 你看的是什么 | 消息里那一段代码块 | 整个 Git 仓 / IDE 工程 | 本机目录 / GitHub 仓 |
| 输出 | 对话里问题 + 改法 | P0/P1/P2 审核报告 | 真改文件（确认后） |
| 会不会动工程 | **否** | 否（只读） | **是** |
| lane | `paste_code` | `code_review` | `code_dev` |
| 需要 Git / Bridge | 否 | Git 或 IDE Bridge | Cursor / local_dev |

**技术上怎么隔开：**

| 点 | 实现 |
|----|------|
| 前端互斥 | `looksLikePasteCodeAnalyze`：若是 Git 审仓且无围栏/裸码 → **false**，让给审码 |
| 部署/提交挡板 | `ChatView`：有 `hasPastedSourceFence` 时**不**走 `looksLikeDeploy` / `looksLikeLocalCommitBatch` |
| 车道登记 | `KNOWN_LANES` 含 `paste_code`；与 `code_review` / `code_dev` 互斥 |
| 系统提示硬禁 | `_PASTE_CODE_ANALYZE_PROMPT`：禁 `request_git_*`、`request_ide_*`、`:::cursor_dev_*`、全仓报告壳 |

### 1.3 为什么要专用车道，而不是「普通聊天随便答」？

**人话：**  
- 没有车道 → 模型可能突然弹出写码选仓卡，或套上「🔍 代码审核报告」全仓壳，用户以为已经审完工程。  
- 有车道 → 明确「只看眼前这段、只在气泡交付、禁止碰 Git/IDE/写码围栏」。

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 围栏探测 | `hasPastedSourceFence` | ``` / ~~~ 且内容够长 |
| 裸码探测 | `looksLikeRawPastedCode` | ≥3 行且代码形态命中 |
| 意图合成 | `looksLikePasteCodeAnalyze` | 围栏(+问法) 或 问法+裸码 |
| 流式选项 | `pasteCodeStreamOpts()` | `{ workbuddyLane:'paste_code', cursorDevLane:false }` |
| 后端解析 | `resolve_workbuddy_lane` / `append_lane_force_routes` | 注入贴码强制路由文案 |

### 1.4 安全上钉死了什么？

| 约束 | 技术实现 |
|------|----------|
| 禁止审仓工具 | 提示 + Skill：不调 `request_git_*` / `request_ide_*` |
| 禁止写码围栏 | 禁止输出 `:::cursor_dev_*` |
| 禁止全仓报告壳 | 禁止 `## 🔍 代码审核报告` 那套终稿格式 |
| 不写磁盘 / 无 Job | 无 Bridge、无 local_dev propose；交付只在 SSE token |
| 短确认续写 | Skill：用户「来吧」须直接贴完整代码，禁止跑题 |

## 2. 实现流程（人话 + 技术点怎么落地）

> 每节先讲「人看到什么 / 为什么这样」，再给 **技术点表** 和调用链。

### 2.1 ChatView 发送顺序：围栏先挡部署/提交

**人话：** 贴了代码块又带「部署/提交」字样时，优先当贴码分析，**不要**误弹部署确认卡或提交批审。审码 / 写码排在贴码之后；裸 Git URL 单独澄清「写还是审」。

```text
ChatView send(content) 大致顺序：
  1. 截图等预分支
  2. !hasPastedSourceFence && looksLikeDeploy          → 功能 10
  3. !hasPastedSourceFence && looksLikeLocalCommitBatch → 功能 09
  4. looksLikePasteCodeAnalyze                         → 本篇（贴码）
  5. !fence && isBareGitRepoUrlMessage                 → 澄清写 vs 审
  6. !fence && (looksLikeGitRepoReview|looksLikeCodeReview) → 功能 07
  7. 写码讨论 / 默认 SSE …
```

**技术点：**

| 点 | 怎么做的 |
|----|----------|
| 围栏挡板 | 步骤 2～3 必须 `!hasPastedSourceFence`，避免贴码误入部署/提交 |
| 贴码优先于审码 | 步骤 4 在步骤 6 之前 |
| 流式 opts | `pasteCodeStreamOpts()` → `page_context.workbuddy_lane=paste_code` |

---

### 2.2 意图怎么判定为贴码？

**人话：** 有像样的代码围栏，再加「有什么问题/怎么改」类问法（或虽无问法但明显不是写码意图）；或者没有围栏但有多行裸码 + 分析问法。若是「审 https://github.com/…」且没有贴码，则**不是**贴码。

```text
looksLikePasteCodeAnalyze(text)                    # chatIntent.js
  ├─ 若 looksLikeGitRepoReview 且无 fence/裸码 → false
  ├─ hasPastedSourceFence → 结合问法 / 非 code_dev
  └─ 或 looksLikeRawPastedCode + 分析问法
       ↓
pasteCodeStreamOpts()
  → workbuddyLane: 'paste_code', cursorDevLane: false
```

**技术点：**

| 点 | 函数 | 怎么做的 |
|----|------|----------|
| 围栏 | `hasPastedSourceFence` | 内容长度门槛，防空围栏 |
| 裸码 | `looksLikeRawPastedCode` | 行数 + 代码形态命中数 |
| 与写码互斥 | `looksLikeCodeDevIntent` 等 | 「本机工程加功能」不进贴码 |

---

### 2.3 Agent 侧：提示块 + Skill 怎么约束？

**人话：** 后端认出 `paste_code` 后，塞进贴码专用系统提示和 Skill。模型通常**不调工具**，直接读用户消息里的代码块；输出问题列表 → 建议 →（用户短确认后）完整改写。

```text
POST /api/chat/stream（page_context.workbuddy_lane=paste_code）
  → resolve_workbuddy_lane() === LANE_PASTE_CODE
  → agent_lane_message 注入【路由·贴码】
  → agent.py 注入 _PASTE_CODE_ANALYZE_PROMPT
  → 加载 Skill paste-code-analyze/SKILL.md

硬约束：
  - 禁止 request_git_* / request_ide_*
  - 禁止 :::cursor_dev_* 写码围栏
  - 禁止「## 🔍 代码审核报告」全仓壳
  - 短确认 → 立刻完整代码，禁止跑题科普
```

**技术点：**

| 点 | 函数 / 模块 | 怎么做的 |
|----|-------------|----------|
| 车道常量 | `workbuddy_lanes.LANE_PASTE_CODE` | 与 sanitize 校验 |
| 强制路由 | `agent_lane_message.append_lane_force_routes` | 贴码文案块 |
| 提示 | `_PASTE_CODE_ANALYZE_PROMPT` | 禁工具、禁围栏、禁报告壳 |
| Skill | `paste-code-analyze` | 交付形态与续写规则 |

---

### 2.4 标准对话时序

**人话：** 第一轮出问题与改法；你说「来吧」后同会话直接贴完整代码。全程没有选仓卡、没有 Job、没有落盘。

```text
轮次 1：用户贴代码 + 问问题
  → SSE token 流式；ChatView 渲染 Markdown 代码块
  → 模型：问题列表 → 修改建议（可含局部 diff 说明）

轮次 2（可选）：用户「来吧 / 好的」
  → 同 thread checkpoint 续写
  → 模型须直接输出完整改后代码
```

**技术点：**

| 点 | 怎么做的 |
|----|----------|
| 无 tool call | 代码在用户消息上下文内，一般不调 Tool |
| 交付物 | 仅消息气泡；不写 `EXPORT_DIR`、不建 local_dev Job |

---

### 2.5 分流对照与排查

| 用户说法 | 意图函数 | lane | 会不会动工程 |
|----------|----------|------|--------------|
| 贴 20 行 +「有啥 bug」 | `looksLikePasteCodeAnalyze` | `paste_code` | 否 |
| 「审 https://github.com/xx」 | `looksLikeGitRepoReview` | `code_review` | 否（只读克隆） |
| 「本机工程加登录页」 | `looksLikeCodeDevIntent` | `code_dev` | 是（Job 后） |
| 贴代码但说「部署到预发」 | 有围栏 → **不**走 deploy | 优先贴码或普通聊 | 否（本篇） |

| 现象 | 人话原因 | 技术上先看 |
|------|----------|------------|
| 弹出 Git 选仓卡 | 误判成审码 | lane 是否为 `code_review`；是否无围栏的 Git 审仓句 |
| 弹出写码确认卡 | 误判成写码或出了围栏 | lane 是否为 `code_dev`；模型是否输出 `:::cursor_dev_*` |
| 短确认后又科普 | Skill/提示未生效 | `paste-code-analyze` 是否加载；`_PASTE_CODE_ANALYZE_PROMPT` |
| 想审全仓 | 能力选错 | 引导改说「审核仓库」走功能 07 |

## 3. 技术及用法（速查）

| 模块 | 关键函数 / 符号 | 干什么 |
|------|-----------------|--------|
| `chatIntent.js` | `hasPastedSourceFence`、`looksLikeRawPastedCode`、`looksLikePasteCodeAnalyze`、`pasteCodeStreamOpts` | 意图与流式选项 |
| `ChatView.vue` | send 分流顺序（deploy/commit → paste → review） | 围栏挡板与 SSE |
| `workbuddy_lanes.py` | `LANE_PASTE_CODE` | 车道登记 |
| `agent_lane_message.py` | `append_lane_force_routes` 等 | 后端强制路由文案 |
| `agent.py` | `_PASTE_CODE_ANALYZE_PROMPT` | 禁 Git/IDE/写码围栏 |
| Skill | `paste-code-analyze` | 对话交付与短确认规则 |

**配置：** 无单独环境开关；依赖现有 `LLM_*` / Deep Agents 即可。不需要 Git、IDE 配对、Cursor Key。

## 4. 后续可以怎么做、不要做什么

**可以做：**

1. 语言/框架探测后给更贴栈的检查清单（仍对话交付）  
2. 显式按钮「把这段改动转到写码车道」（须再确认，勿自动）  

**不要做：**

1. 贴码分析偷偷克隆仓库或写本机文件  
2. 与全仓审码报告格式混用，让用户以为已经审完工程  
3. 贴码车道放开 `request_git_*` / `request_ide_*` / `:::cursor_dev_*`

## 自测路径（验收）

1. 贴一段有明显空指针风险的 JS/Python，问「有什么问题」→ 应进贴码，出问题列表，**不**弹选仓卡。  
2. 回「来吧」→ 应直接给完整修改，而不是写码确认卡或 PCB 科普。  
3. 消息含代码围栏且带「部署」字样 → **不应**误入功能 10 部署确认。  
4. 「审核 https://github.com/org/repo」（无贴码）→ 应走功能 07，不进本篇。
